# СмакПлан

Локальний AI-помічник: рецепт і покупки в «Сільпо» за кількістю порцій та бюджетом. Next.js, TypeScript, Tailwind CSS, OpenAI Agents SDK і офіційний MCP.

Документація для розробки: [docs](docs/README.md) — архітектура, API,
інтеграції, перевірки та межі безпеки. Інструкції для агентів — [AGENTS.md](AGENTS.md).

## Запуск

Потрібен Node.js 22 або новіший.

```sh
npm ci
npm run dev
```

Відкрити **http://127.0.0.1:3000**. Використовувати саме цю адресу, а не `localhost`: вона є OAuth callback origin за замовчуванням.

У наявному `.env` потрібен `OPENAI_API_KEY`. Не додавайте ключ до Git. Не змінюйте його назву на `NEXT_PUBLIC_*`.

Додаткові змінні наведено в `.env.example`:

- `OPENAI_MODEL` — необов’язкова модель; інакше використовується default встановленої версії Agents SDK.
- `APP_ORIGIN` — адреса застосунку, за замовчуванням `http://127.0.0.1:3000`. При зміні порту змініть і цю адресу та підключіть Сільпо повторно.

Натиснути «Підключити Сільпо», самостійно пройти вхід та повернутися до форми. Акаунт має містити кошик із магазином/доставкою та чинним слотом. Налаштовувати його потрібно на silpo.ua. Застосунок не створює й не змінює кошик.

OAuth використовує discovery, Dynamic Client Registration, PKCE та перевірку state через MCP SDK. Токени й PKCE зберігаються лише у пам’яті серверного процесу; браузер отримує HttpOnly cookie з випадковим ідентифікатором. Сесія діє до 8 годин; перезапуск сервера її скидає. Це демо для одного локального користувача, не конфігурація для багатокористувацького чи serverless deployment.

## Як працює підбір

1. Сервер отримує живий `tools/list`. Модель бачить тільки локально описані пошук і перегляд каталогу; аргументи перевіряються локально та додатково за схемою MCP через Ajv.
2. Сервер читає поточний кошик, його деталі й слоти; перевіряє час, тип доставки та `available=true` кодом. Підтверджений контекст додається сервером до пошукових аргументів.
3. Зберігає рецепт та незмінні кількості інгредієнтів.
4. Викликає дозволені MCP-tools пошуку, прив’язує вибрані товари до конкретних об’єктів відповіді. Сервер отримує деталі за справжніми slug для посилань.
5. Типізований адаптер читає поля каталогу, перевіряє магазин, ідентичність товару та наявність пропозиції, розраховує упаковки й суму в копійках та зберігає найкращий знайдений варіант. Ціни беруться з пошуку, а URL — з деталей.
6. До трьох раундів пошуку дешевших брендів/фасувань; завершення при досягненні бюджету або відсутності покращення. Загальний таймаут — 180 секунд, максимум 45 логічних викликів пошуку й деталей (без bootstrap, discovery та транспортних повторів), до двох повторів тимчасової MCP-помилки.

`POST /api/recipe-plan`: `{ "request": "Лазанья", "servings": 4, "budgetUah": 600 }`.
Результат: рецепт, товари, `totalKop`, `budgetKop`, `differenceKop`, `status`, `missing`, `substitutions`, магазин і час перевірки цін. Можливі статуси: `within_budget`, `over_budget`, `incomplete`.

Повторне використання одного товару агрегується перед округленням упаковок. Усі інгредієнти купуються; доставка не враховується. За неповних даних показується лише підтверджена частина суми. Найдешевший серед перевірених варіантів не означає глобально мінімальну ціну.

## Межі перевірки інтеграції

27.09.2026 схеми та поля адаптера звірено з авторизованим `tools/list` і реальними відповідями каталогу. `weighted=true` означає ціну й крок покупки в кілограмах, навіть якщо `displayRatio` дорівнює `100г`. `weighted=false` означає упаковки, вміст яких указаний у `displayRatio`. Додатково перевіряється узгодженість `price` та `displayPrice`. Семантичне зіставлення інгредієнта з товаром виконує модель — це не детермінований доказ кулінарної еквівалентності.

Непідтримані або неоднозначні поля відхиляються й дають `incomplete`, а не вигадані ціни. Посилання зі slug не конструюються. Для вагових товарів потрібен явний крок продажу; кількість не може перевищувати `stock`. Фото може бути відсутнім — є заглушка. Грами й мілілітри не прирівнюються: наприклад, рецепт може початково задавати молоко у грамах для кухонних ваг, або підбирається товар із фасуванням у літрах.

## Перевірки

Prettier використовує стиль із `mf-project`: одинарні лапки, крапки з комою,
відступ у 2 пробіли, ширину 80 символів і LF. ESLint поєднує правила Next.js,
TypeScript, Prettier та сортування імпортів, інтерфейсів і JSX-props із цього ж
проєкту. Згенеровані файли, кеші та локальні env-файли виключені з форматування.

```sh
npm run lint          # перевірити код без змін, попередження теж блокують
npm run lint:fix      # автоматично виправити підтримувані правила
npm run format       # відформатувати проєкт
npm run format:check # перевірити форматування без змін
```

Для сумісності `typescript-eslint` збережено компілятор TypeScript 7 під alias
`@typescript/native`, а пакет `typescript` посилається на сумісний API TypeScript 6.
`npm run typecheck` використовує `tsc` версії 7. ESLint 9 узгоджений із peer-залежностями
React-плагінів конфігурації Next.js.

```sh
npm test
npm run typecheck
npm run build
```

Окрема коротка перевірка ключа й Agents SDK: `npm run smoke:openai`. Вона робить реальний платний API-запит, викликає арифметичний tool і перевіряє структуровану відповідь; ключ та вміст відповіді не друкуються.

Тести використовують явно синтетичні приклади; вони не підміняють реальні MCP-відповіді в застосунку. Для live smoke test підключіть акаунт, введіть «Лазанья», 4, 600 і перевірте: товарні посилання, кількості упаковок, арифметику та статус. Вкладання в 600 грн залежить від актуального каталогу.

Для production build локально: `npm run build`, потім `npm start`.

Перевірений live-сценарій 27.09.2026: лазанья на 4 людей із бюджетом 600 грн. Повернуто повний рецепт і 12 товарів із завантаженими фото 50×50 та URL із MCP. Після оптимізації знайдений кошик коштував 819,14 грн, статус `over_budget`, перевищення 219,14 грн. Це знімок конкретного запуску й магазину, не обіцянка майбутньої ціни. Жоден товар не додавався до кошика.

Tracing Agents SDK вимкнено; вхідні URL не логуються, щоб OAuth-коди не потрапляли в консоль. Ключі й токени не повертаються клієнту. Виклики запису MCP відсутні в allowlist.

## Захист від prompt injection

Модель не є межею авторизації. Навіть якщо вона підкориться шкідливому тексту, код обмежує доступні операції:

- Модель отримує лише `silpo_find_products_batch` і `silpo_get_products` із локальними описами та строгими схемами. Описи й схеми віддалених інструментів не передаються моделі; схема MCP використовується тільки для додаткової серверної перевірки. Читання кошика та деталей виконує сервер.
- Магазин і слот підставляє сервер. Модель не може передати власні `branchId`, `shoppingCartId`, URL або додаткові аргументи. Кожний фактичний MCP-виклик окремо перевіряє allowlist читання.
- Із пошукових відповідей залишаються лише поля типізованих товарів у стандартних масивах. Довільні `instructions`, `meta`, описи й вкладені підроблені об’єкти відкидаються. Товар реєструється лише за канонічним шляхом; ціни та ідентичність перевіряються кодом. Назви товарів залишаються недовіреними даними.
- Повідомлення про оптимізацію містить тільки номер раунду, суму й кількість відсутніх інгредієнтів. Текст каталогу не вставляється в системні інструкції або нове повідомлення користувача. Зображення й ідентифікатор магазину вилучаються з пошукових даних для моделі.
- Один товар не можна призначити різним найменуванням інгредієнтів. Для повторного використання того самого інгредієнта рецепт має використовувати однакову канонічну назву; кількості агрегуються. Це вузька перевірка очевидної підміни, а не доказ кулінарної відповідності.
- Фото товарів дозволені лише з перевіреного CDN `images.silpo.ua`; інші адреси дають заглушку. React відображає відповіді як текст. Розміри рецептів, аргументів і результатів обмежені; відповідь моделі має ліміт 6000 токенів на виклик.

Автоматичні тести перевіряють ці детерміновані межі, включно з викликом строгого інструмента Agents SDK із підробленими аргументами. Вони не перевіряють успішність jailbreak проти живої моделі. Після посилення живий наскрізний прогін із OpenAI/Сільпо не повторювався; зміни сумісні з локально збереженим форматом batch-пошуку, а непідтриманий формат відхиляється.

**Абсолютна невразливість не гарантується.** Модель усе ще визначає страву, кулінарні кроки й семантичну відповідність окремого товару інгредієнту. Шкідливий текст може вплинути на ці рішення. Відсутність витоку ключів чи можливості змінити кошик не означає безпомилковий рецепт. Для публічного запуску потрібні окремі живі adversarial-evals, квоти та перегляд моделі загроз.
