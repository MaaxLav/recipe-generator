# Межі безпеки

Цей документ описує поточні контролі й правила збереження цих контролів,
а не сертифікацію невразливості. Підтримуване розгортання — персональний
loopback-сервер; публічний доступ потребує окремого перегляду.

## Секрети та браузер

- OpenAI key і OAuth credentials залишаються на сервері. Модель не отримує
  сесію, tokens або verifier як інструментальний контекст.
- Сесія в браузері — HttpOnly cookie з випадковим ID; перевіряються строк
  життя, OAuth state і PKCE. Деталі — в [інтеграціях](integrations.md).
- `POST /api/recipe-plan` вимагає точний Origin, JSON та авторизовану сесію.
- Tracing SDK вимкнено. [next.config.ts](../next.config.ts) вимикає логування
  вхідних URL і browser-to-terminal та встановлює no-referrer, nosniff, DENY.
- Не повертайте клієнту raw SDK-помилки й не логуйте авторизаційні заголовки,
  callback URL, токени або вміст `.env`. Перевіряйте ключ лише за наявністю.

## Недовірений текст і повноваження моделі

User request, MCP metadata, назви й інші поля товарів можуть містити інструкції.
Не підвищуйте їх до system/developer-повідомлень чи нових дозволів.

Кодом забезпечується:

1. Локальні строгі catalog-контракти та окрема перевірка allowlist на dispatch.
   Відсутні write, checkout, shell, filesystem і довільний HTTP tool.
2. Магазин/слот додає сервер; модель не може підмінити їх аргументами.
3. Очищення MCP-пошуку до типізованих товарів, канонічні JSON Pointers,
   own-property перевірки й заборона prototype traversal.
4. Перевірка ID/slug/магазину, пропозиції, ціни, фасування та залишку товару.
5. Фіксація рецепта, контроль призначень і серверна арифметика. Один ID товару
   не може представляти різні нормалізовані назви інгредієнтів.
6. У нове повідомлення оптимізації потрапляють лише числові підсумки; історія
   tool-повідомлень зберігається і все ще містить недовірені назви товарів.

`catalogForModel` прибирає з пошукової проєкції `image` і `branchId`. Це не
твердження, що модель ніколи не бачить товарних URL: нормалізовані товари
повертаються також локальними `register_products` та `evaluate_basket`.
Не додавайте до жодного такого результату credentials або raw account data.

## Відображення

React виводить рецепт і товари як текст без HTML/Markdown-інтерпретації.
Посилання й фото проходять URL-перевірки. Фото товарів завантажуються браузером
із no-referrer, а не довільним серверним image proxy. Поточна URL-перевірка
контролює початкову адресу, не поведінку редиректів зовнішнього сервера.

## Чого ці контролі не доводять

- Відповідність окремого товару інгредієнту, коректність кроків і безпечність
  рецепта залишаються семантичними рішеннями моделі. Перевірка однакового
  product ID для різних назв блокує лише один клас очевидних підмін.
- Зовнішній MCP визначає фактичну поведінку read-tools і правдивість каталогу.
- Таймаути й лічильники обмежують один запит, але не загальні витрати акаунта.
- Ліміт тіла HTTP та розміру MCP-відповіді перевіряється після їх отримання;
  це не повноцінний потоковий захист від великих даних.
- Сесії в пам’яті, ліміт 100 сесій та unauthenticated OAuth start не є
  багатокористувацькою системою квот і захисту від DoS.

[Локальні тести](development.md) перевіряють детерміновані межі, не універсальну
стійкість живої моделі до prompt injection. Змінюючи безпекові правила,
додавайте негативні регресії й позитивний звичайний сценарій, описуйте залишкові
ризики та окремо зазначайте, чи виконували живі adversarial-перевірки.
