# Інтеграції

## OpenAI Agents SDK

[createPlan](../src/server/agent.ts) створює один `Agent` і `Runner` на запит.
Ключ читається лише на сервері з `OPENAI_API_KEY`; `OPENAI_MODEL` необов’язковий.
Tracing вимкнено, паралельні tool calls вимкнено, `maxTokens=6000` на відповідь
моделі. Початковий запуск має `maxTurns=18`, кожен раунд оптимізації — 10.

Модель використовує catalog-tools і три локальні інструменти:
`define_recipe`, `register_products`, `evaluate_basket`. Перелік полів та їх
обмеження беруться з локальних схем. Структурований фінальний `message`
моделі не використовується замість перевіреного серверного `PlanResult`.

## Silpo MCP і OAuth

Endpoint — `https://mcp.silpo.ua/mcp`; транспорт — Streamable HTTP MCP SDK.
[session.ts](../src/server/session.ts) реалізує OAuth provider; SDK обробляє
discovery, реєстрацію клієнта, PKCE та токени.

Cookie містить випадковий 32-байтовий ID, а не токен. Налаштування: HttpOnly,
SameSite=Lax, Path=/, 8 годин; Secure вмикається для HTTPS `APP_ORIGIN`.
Map у пам’яті тримає максимум 100 сесій. OAuth state має 10-хвилинне вікно,
перевіряється timing-safe порівнянням і споживається до обміну коду.
Перезапуск процесу скидає всі сесії.

## Контекст покупки

Перед викликом моделі сервер читає:

1. `silpo_get_my_shopping_cart` → ідентифікатор наявного кошика.
2. `silpo_get_shopping_cart_by_id` → `shipments[0].branchId`, тип доставки й слот.
3. `silpo_get_time_slots` → підтвердження доступності вибраного інтервалу.

Початок і кінець слота мають точно збігатися, `available` бути true, тип
доставки відповідати, а кінець слота — бути в майбутньому.
`DeliveryExpressByPromise` нормалізується до `DeliveryHome`.
Мульти-магазинне планування не реалізоване: використовується перший shipment.
Якщо контекст відсутній, користувач налаштовує його на сайті Сільпо.

## Два рівні доступу до інструментів

[READ_TOOLS](../src/lib/mcp-policy.ts) обмежує discovery і кожний фактичний
виклик. Він містить інструменти кошика, слотів, пошуку, деталей, а також
`silpo_get_similar_products` і `silpo_get_replacements`.

Модель бачить **лише два MCP-tools**, визначені в
[agent-policy.ts](../src/lib/agent-policy.ts):

Спільні Zod-схеми аргументів і товарів визначені в
[types/catalog.ts](../src/types/catalog.ts) та експортовані через
[types/index.ts](../src/types/index.ts). Політики викликів і проєкція відповіді
залишаються в `agent-policy.ts`, нормалізація — у `silpo-product.ts`.

| Tool                        | Аргументи моделі                                                                                        |
| --------------------------- | ------------------------------------------------------------------------------------------------------- |
| `silpo_find_products_batch` | `products`: 1–30 назв до 120 символів; `limit`: 1–20                                                    |
| `silpo_get_products`        | `limit`: 1–20; nullable `category`, `offset` (0–200), `sortBy`, `sortDirection`, `fromPrice`, `toPrice` |

Nullable поля у строгій схемі передаються як `null`, коли не потрібні;
сервер вилучає їх перед MCP-викликом. Він також додає підтверджені
`branchId`, `deliveryType`, `timeslotStart`, `timeslotEnd` та `inStock=true`
для перегляду каталогу. Остаточні аргументи додатково перевіряє Ajv за
живою схемою tools/list. Віддалені описи не стають інструкціями моделі.

Наявність інструмента в `READ_TOOLS` не означає, що модель може його викликати.
Деталі товару завантажуються сервером при реєстрації; cart-tools моделі не видимі.

## Дані товарів

`callReadTool` використовує `structuredContent`, а за його відсутності —
JSON із текстових блоків. Проєкція пошуку приймає `queries[].products[]`
для batch та `products[]` для перегляду каталогу. Зайві поля відкидаються,
невалідний товар стає `null` зі збереженням індексу. Канонічні шляхи:
`/queries/N/products/N` та `/products/N`.

[Адаптер](../src/lib/silpo-product.ts) звіряє ID, slug, магазин, доступність,
залишок і пропозицію в деталях. Ціна й фасування беруться з пошуку, URL —
із деталей. Посилання не будується припущенням зі slug.

- `weighted=true`: `price`, `step`, `stock` трактуються для продажу в кг;
  `displayRatio` може бути `100г`. Перевіряється узгодженість `displayPrice`.
- `weighted=false`: ціна за упаковку, її вміст береться з `displayRatio`,
  крок має бути цілим. Допуск узгодження показаної ціни — одна копійка.
- Немає достовірного фасування, URL чи ціни — товар не реєструється.
  Немає фото — допустима заглушка.
- Product URL: HTTPS `silpo.ua` або піддомен. Фото: HTTPS `images.silpo.ua`.
  Credentials і нестандартний порт в URL заборонені.

## Ліміти й відмови

| Межа                                    | Поточна поведінка                                                         |
| --------------------------------------- | ------------------------------------------------------------------------- |
| Увесь план                              | 180 с на сервері; 185 с у браузері                                        |
| Один MCP fetch/tool call                | 30 с                                                                      |
| Пошук і деталі                          | Лічильник до 45 логічних викликів за план; cache hit деталей не рахується |
| Початковий контекст, discovery, retries | Не входять у лічильник 45; обмежені часом запиту                          |
| Тимчасова MCP-помилка                   | До двох повторів для 429, 5xx або TypeError; 401/403 не повторюються      |
| Пошукова відповідь                      | Перевірка JSON-довжини до 200000 символів після отримання                 |
| Паралельність                           | Один активний план на сесію; глобальної квоти немає                       |

За зміни upstream-схеми спочатку перевірте актуальний tools/list і мінімальний
приклад відповіді. Збережіть лише знеособлений fixture, оновіть локальні схеми,
адаптер і тести. Не послаблюйте валідацію та не відкривайте довільні tools лише
для усунення помилки. `.cache/silpo` може містити локальні діагностичні знімки;
вона не є runtime-залежністю чи джерелом даних для користувача.
